## 1. System Overview & Core Principles

**Goal**: A self-service, per-user VPN gateway where each user receives a dedicated WireGuard tunnel with DNS-based content filtering, orchestrated by Kubernetes. Strong binding between authenticated user and VPN tunnel is enforced via a per-session pre-shared key (PSK).

**Primary Innovations**:
- **Session-bound PSK**: Prevents generic WireGuard clients from connecting.
- **Per-user pod isolation**: Dedicated pod with its own WireGuard interface and network policies.
- **API-driven provisioning**: REST API manages user lifecycle and key exchange.
- **Internal security layer**: OPNsense handles TLS termination, reverse proxy, and UDP forwarding, positioned behind an external edge router.

**Constraints & Scope**:
- iOS support removed (Apple Developer Program cost barrier).
- AdGuard Home replaces Pi-hole for richer API and per-client filtering.
- University science project – maintainable, not enterprise-grade.
- Target scale: hundreds of users on commodity hardware (Proxmox/K3s).

**Network Topology Summary**:
```
Internet → External Edge Router (port forwarding) → OPNsense (TLS, UDP forward, CrowdSec, Suricata on LAN) → K3s Cluster (MetalLB, user pods, AdGuard Home)
```

## 4. WireGuard Operator – Full Lifecycle

### 4.1 On Create

1. Generate server WireGuard keypair (if not pre-existing per user).
2. Allocate a unique VPN subnet (`10.0.x.0/24`) and assign server IP `10.0.x.1/24`, client IP `10.0.x.2/32`.
3. Create a Pod with WireGuard container and iptables rules (see Section 5).
4. Create a Service of type `LoadBalancer`; MetalLB assigns an external IP from its pool.
5. Register client in AdGuard Home using pod's cluster IP (`status.podIP`) and tags derived from `filteringProfile` (see Section 6).
6. Update CRD `status` with `podName`, `podIP`, `endpointIP`, `endpointPort`, `vpnServerIP`.

### 4.2 On Update

1. Detect changes to `spec.clientPublicKey`, `spec.presharedKey`, or `spec.filteringProfile`.
2. Rewrite `/etc/wireguard/wg0.conf` inside the pod.
3. Apply changes atomically without disrupting the interface:
   ```bash
   wg syncconf wg0 <(wg-quick strip wg0)
   ```
4. If `presharedKey` is **removed** (logout/revocation):
   - Remove peer immediately from the kernel:
     ```bash
     wg set wg0 peer <client_pubkey> remove
     ```
   - Wait 5 seconds to allow in-flight UDP packets to be dropped (prevents ICMP port unreachable noise).
   - Optionally delete the pod if the session is terminated.
5. If `filteringProfile` changed:
   - Update AdGuard Home client tags via API (`PUT /control/clients/update`).

### 4.3 On Delete

1. Remove peer from WireGuard (if still present).
2. Delete AdGuard Home client entry using stable name `user-<username>` (remove pod IP from `ids` list; delete client if no IPs remain).
3. Delete the pod and the associated Service.
4. MetalLB releases the external IP back to the pool.

### 4.4 Implementation Notes

- **Safe reload**: `wg syncconf` compares current kernel state with desired configuration and applies only necessary changes. Avoid restarting the `wg-quick` service.
- **Immediate revocation**: `wg set ... peer remove` deletes the peer from the kernel instantly; any existing session keys become useless.
- **Grace period**: A 5-second sleep after peer removal before pod deletion prevents the kernel from sending ICMP port unreachable responses to the client's final keepalives.
- **Operator RBAC**: The operator needs permissions to create/update/delete Pods, Services, and ConfigMaps (if storing keys), and to read/update the `WireGuardUser` CRD.

## 5. User VPN Pod Design

### 5.1 Container Image

Custom Alpine-based image including:
- `wireguard-tools`
- `iptables`
- Health check script (e.g., check `wg show` for handshake)

### 5.2 Environment Variables

Passed by the operator:
- `WG_SERVER_PRIVATE_KEY`
- `WG_SERVER_PORT=51820`
- `WG_PEER_PUBLIC_KEY`
- `WG_PEER_PSK`
- `WG_PEER_ALLOWED_IPS`

### 5.3 WireGuard Configuration (`wg0.conf`)

```ini
[Interface]
PrivateKey = <server_private_key>
Address = 10.0.1.1/24
ListenPort = 51820
PostUp = ip link set dev wg0 mtu 1420
PostUp = iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE
PostUp = iptables -t nat -A PREROUTING -i wg0 ! -s 10.0.1.1 -p udp --dport 53 -j DNAT --to-destination 10.43.0.10:53
PostUp = iptables -t nat -A PREROUTING -i wg0 ! -s 10.0.1.1 -p tcp --dport 53 -j DNAT --to-destination 10.43.0.10:53
PostDown = iptables -t nat -D POSTROUTING -o eth0 -j MASQUERADE
PostDown = iptables -t nat -D PREROUTING -i wg0 ! -s 10.0.1.1 -p udp --dport 53 -j DNAT --to-destination 10.43.0.10:53
PostDown = iptables -t nat -D PREROUTING -i wg0 ! -s 10.0.1.1 -p tcp --dport 53 -j DNAT --to-destination 10.43.0.10:53

[Peer]
PublicKey = <client_public_key>
PresharedKey = <psk>
AllowedIPs = 10.0.1.2/32
PersistentKeepalive = 25
```

### 5.4 DNS Hijacking Exemption Explained

- **`! -s 10.0.1.1`**: Exempts DNS queries originating from the pod's own WireGuard interface IP (the server itself). Without this exemption, if the pod's `/etc/resolv.conf` points to AdGuard Home, the pod's own DNS queries would be caught in the DNAT rule, creating a routing loop and breaking health checks.
- **Alternative approach**: Configure the pod's `/etc/resolv.conf` to use a public DNS (e.g., `1.1.1.1` or `8.8.8.8`). This entirely avoids the loop without needing the exemption rule. Choose whichever fits your security posture.

### 5.5 MTU Sizing

- **Standard Ethernet (1500 MTU)**: Set `wg0` MTU to **1420** (1500 - 60 bytes WireGuard overhead).
- **PPPoE (1492 MTU)**: Set to **1412**.
- **Mobile networks (often 1280)**: Set to **1280** as fallback (can be configurable per user).

### 5.6 PersistentKeepalive

- Set to `25` seconds. This sends a small keepalive packet every 25 seconds, maintaining NAT bindings on the client's router. Without this, inbound traffic stops after the NAT timeout (typically 30–120 seconds).

## 6. AdGuard Home Integration – Per-User DNS Filtering

### 6.1 Deployment

- **StatefulSet** with PersistentVolumeClaim for `/opt/adguardhome/conf` and `/opt/adguardhome/work`.
- Service type `ClusterIP` with a static IP, e.g., `10.43.0.10`.
- Web UI and API exposed on port `3000` (internal only).
- Admin credentials stored in a Kubernetes Secret.

### 6.2 API-Driven Client Management (Operator Logic)

```python
# Stable client identifier (survives pod IP changes)
client_name = f"user-{username}"

# On pod creation (pod_ip from status.podIP)
adguard_api.post("/control/clients/add", {
    "name": client_name,
    "ids": [pod_ip],                     # Pod's cluster IP (e.g., 10.42.2.5)
    "use_global_settings": False,
    "filtering_enabled": True,
    "parental_enabled": profile == "strict-parental",
    "safebrowsing_enabled": True,
    "safesearch_enabled": True,
    "tags": profile_to_tags[profile]     # e.g., ["block_ads", "safe_search"]
})

# On pod IP change (rescheduling): update, don't delete
adguard_api.put("/control/clients/update", {
    "name": client_name,
    "data": {
        "ids": [new_pod_ip, old_pod_ip]  # Keep both during migration
    }
})
# After graceful migration, remove old IP.

# On pod deletion
adguard_api.delete(f"/control/clients/{client_name}")
```

### 6.3 Tag-Based Filtering Profiles

Pre-configure tags in AdGuard Home (e.g., `block_ads`, `safe_search`, `block_adult`, `block_social`). Map user profiles to tag lists:
- `strict-parental` → `["block_ads", "safe_search", "block_adult"]`
- `basic` → `["block_ads"]`
- `unfiltered` → `[]`

### 6.4 Why Source IP Matching Works

- Pod uses SNAT (MASQUERADE) for outbound traffic from VPN clients.
- All DNS queries appear to AdGuard Home with source IP = pod's `eth0` IP (Kubernetes cluster IP).
- Since each user pod has a unique cluster IP, per-user filtering is automatic.

### 6.5 Performance Tuning

- Enable prefix-tree indexing (AGH default) for O(1) rule lookups.
- Increase `ratelimit` in AGH config to prevent abuse.
- Use multiple upstream DNS servers for redundancy.

## 7. Authentication & Session Binding Flow

### 7.1 Complete Sequence

1. **Login**:
   - Client app → `POST /auth/login` with email/password.
   - Backend validates, returns JWT (expires 1 hour).

2. **Key Exchange**:
   - Client generates ephemeral Curve25519 keypair locally. Private key stored in Android Keystore / OS credential manager.
   - Client → `POST /api/v1/tunnel/keys` with header `Authorization: Bearer <jwt>` and body `{"client_pubkey": "..."}`.
   - Backend:
     - Verifies JWT.
     - Generates a 32-byte PSK using CSPRNG (`secrets.token_bytes(32)`).
     - Updates `WireGuardUser` CRD: sets `spec.clientPublicKey`, `spec.presharedKey`, `spec.sessionExpiry`.
   - Operator reconciles, writes `wg0.conf`, applies with `wg syncconf`.

3. **Response to Client**:
   ```json
   {
     "server_pubkey": "<base64>",
     "psk": "<base64>",
     "vpn_ip": "10.0.1.2/32",
     "endpoint": "vpn.example.com:51820",
     "dns_server": "10.43.0.10"
   }
   ```

4. **Client Configuration**:
   - Client writes WireGuard configuration with received parameters.
   - Sets `PersistentKeepalive = 25` in its peer section.
   - Initiates handshake.

5. **Logout / Revocation**:
   - Client → `POST /auth/logout` (or token expiry).
   - Backend removes `spec.presharedKey` from CRD.
   - Operator detects removal, runs `wg set wg0 peer <pubkey> remove`.
   - After 5-second grace period, pod may be deleted.

### 7.2 Security Properties

- **Client private key never leaves the device**.
- **PSK is per-session**, cryptographically binding client to server.
- **Generic WireGuard clients cannot connect** because they cannot obtain the session PSK via authenticated API.
- **Revocation is immediate** via peer removal; no waiting for key rotation.

## 8. Network Architecture: External Edge Router + Internal OPNsense

### 8.1 Topology Overview

```
Internet
    │
    ▼
[ External Edge Router ]
  (ISP gateway, basic NAT router, or dedicated pfSense)
  Public IP: <dynamic or static>
  Port forwards:
    - TCP 443 → OPNsense WAN IP
    - UDP 51820 → OPNsense WAN IP
    │
    ▼
[ OPNsense VM (Internal) ]
  WAN Interface: 192.168.1.10/24 (example)
  LAN Interface: 10.0.0.1/24 (connected to K3s network)
  - Caddy: terminates TLS, proxies to Traefik ingress
  - Firewall: allows TCP 443, UDP 51820 on WAN
  - NAT: forwards UDP 51820 to MetalLB IP range
  - CrowdSec: analyzes Caddy logs, blocks IPs
  - Suricata: IDS on LAN interface (inspecting decapsulated traffic)
    │
    ▼
[ K3s Cluster Network - 10.0.0.0/24 ]
  - Traefik ingress: receives API traffic from Caddy
  - MetalLB: assigns external IPs from pool 10.0.0.100-10.0.0.200 to user pod services
  - User pods: listen on UDP 51820
  - AdGuard Home: ClusterIP 10.43.0.10
```

### 8.2 External Edge Router Configuration

Simple port forwarding:
- TCP port 443 → OPNsense WAN IP (e.g., 192.168.1.10:443)
- UDP port 51820 → OPNsense WAN IP (e.g., 192.168.1.10:51820)

No other special configuration needed; OPNsense handles all security and proxying.

### 8.3 OPNsense Configuration – WAN Side

**WAN Interface**:
- IP address: static or DHCP from edge router's LAN subnet.
- Firewall Rules (WAN):
  1. **Allow TCP 443** – Destination: This Firewall (for Caddy)
  2. **Allow UDP 51820** – Destination: This Firewall (for WireGuard forwarding)

**NAT Port Forward for WireGuard**:
- Interface: WAN
- Protocol: UDP
- Destination Port: 51820
- Redirect Target IP: **MetalLB IP range** (e.g., `10.0.0.100-10.0.0.200`). OPNsense will forward packets to the specific MetalLB IP because the packet's destination IP is the external IP assigned to that user's service.

**Caddy Reverse Proxy**:
- Plugin: `os-caddy` from OPNsense repository.
- Caddyfile:
  ```caddy
  api.vpn-project.example {
      reverse_proxy http://10.0.0.50:80 {   # Traefik ingress IP
          header_up Host {host}
      }
      tls {
          dns cloudflare {env.CF_API_TOKEN}
      }
      rate_limit {
          zone dynamic {
              key {remote_host}
              events 10
              window 10s
          }
      }
  }
  ```

### 8.4 OPNsense Configuration – Internal Side

**LAN Interface**:
- IP: 10.0.0.1/24 (gateway for K3s nodes).
- **Suricata IDS**: Enable on LAN interface in IDS mode (alert only). This inspects traffic after VPN decapsulation, analyzing actual content without wasting CPU on encrypted WireGuard handshakes. **Do not place Suricata on WAN for WireGuard traffic** because it processes packets before firewall rules in inline mode, causing unnecessary CPU load and potential false positives.

**CrowdSec**:
- Installed via OPNsense plugin.
- Configured to read Caddy access logs.
- Automatically blocks malicious IPs at the firewall level.

### 8.5 MetalLB Configuration

- Mode: Layer2.
- IP Address Pool: `10.0.0.100-10.0.0.200` (must be in the same subnet as OPNsense LAN interface).
- Each user's Service gets a unique external IP from this pool.
- OPNsense forwards UDP packets to the appropriate MetalLB IP; because OPNsense and MetalLB IPs are on the same broadcast domain, ARP works and packets are delivered directly.

### 8.6 Traffic Flow Example (WireGuard)

1. Client sends WireGuard handshake to `vpn.example.com:51820`.
2. DNS resolves `vpn.example.com` to the public IP of the edge router (or a dynamic DNS hostname).
3. Edge router forwards UDP packet to OPNsense WAN IP:51820.
4. OPNsense NAT rule redirects the packet to the MetalLB IP assigned to that user's pod (e.g., `10.0.0.101`).
5. MetalLB (via ARP) delivers the packet to the node hosting the pod, then to the pod's `eth0` interface.
6. Pod's WireGuard processes the handshake.

### 8.7 Security Benefits of This Architecture

- **Defense in depth**: Edge router provides first line of NAT; OPNsense is second layer.
- **Suricata on LAN inspects plaintext**: No wasted CPU on encrypted WireGuard packets.
- **CrowdSec protects API**: Blocks brute-force attempts before they reach K3s.

## 9. Network Performance Optimization

### 9.1 BBR Congestion Control – Important Clarification

- BBR affects only TCP connections where the host is an **endpoint**. For VPN traffic, the TCP endpoints are the client device and the destination server. Enabling BBR on K3s nodes (`net.ipv4.tcp_congestion_control=bbr`) only improves control-plane TCP (e.g., API calls, image pulls). It does **not** improve user VPN throughput.
- **Action**: Do not prioritize BBR tuning for VPN performance. Focus on UDP and WireGuard-specific optimizations.

### 9.2 UDP Buffer Sizing (Critical for WireGuard Throughput)

Apply to all K3s worker nodes (`/etc/sysctl.d/99-wireguard.conf`):
```bash
net.core.rmem_max = 134217728   # 128 MiB
net.core.wmem_max = 134217728
net.core.rmem_default = 16777216
net.core.wmem_default = 16777216
net.ipv4.udp_mem = 134217728 134217728 134217728
net.ipv4.udp_rmem_min = 16384
net.ipv4.udp_wmem_min = 16384
```
Apply with `sysctl -p /etc/sysctl.d/99-wireguard.conf`.

### 9.3 NIC Offload Tuning

Run on K3s node startup (or via systemd service):
```bash
# Enable Generic Receive Offload (GRO) – batches packets, reduces CPU
ethtool -K eth0 gro on
# Disable Large Receive Offload (LRO) – interferes with tunnels
ethtool -K eth0 lro off
# Increase ring buffer sizes to prevent drops under load
ethtool -G eth0 rx 4096 tx 4096
```

**Why these settings**:
- **GRO**: Coalesces incoming packets, reducing per-packet processing overhead.
- **LRO**: Can merge packets across different flows; breaks encapsulation protocols like WireGuard, must be disabled.
- **Ring buffer**: Larger buffers reduce packet loss during bursts.

### 9.4 Queue Management (SQM) – Bufferbloat Mitigation

- **Placement**: On the egress of the **external edge router** (if it supports SQM), or on OPNsense WAN interface (if edge router is dumb). The ideal location is the actual bottleneck link—usually the edge router's WAN interface.
- **OPNsense Traffic Shaper**: If applying on OPNsense, create a pipe with bandwidth set to 95% of actual upload speed. Apply **FQ-CoDel** or **CAKE** queue discipline.
- **Effect**: Reduces latency under load from >100ms to <20ms for interactive traffic.

**CAKE vs FQ-CoDel**:
- **FQ-CoDel**: Lighter weight, suitable for most hardware.
- **CAKE**: More advanced fairness and per-host isolation, but higher CPU usage. Choose based on node capabilities.

### 9.5 CPU Affinity & IRQ Balance

- Enable `irqbalance` service on K3s nodes.
- For high throughput (>500 Mbps aggregate), manually pin NIC queues to specific CPU cores using `/proc/irq/<irq>/smp_affinity`.

**Example**: Check `/proc/interrupts` to find IRQ numbers for your NIC, then set affinity mask:
```bash
echo 2 > /proc/irq/123/smp_affinity   # Pin to CPU1
```

### 9.6 Additional Tuning (Optional)

- **RPS/RFS**: Receive Packet Steering can distribute packet processing across CPUs when NIC lacks multi-queue support.
- **XPS**: Transmit Packet Steering for egress balancing.
