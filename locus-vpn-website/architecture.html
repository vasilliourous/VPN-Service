How Locus is put together

The design decisions behind the client and the network, with the reasoning for each. Written for people who want to check the work rather than take a slogan on trust.

1. A TUN device, not a proxy

Older designs in this family ran a SOCKS5 proxy on the local machine and asked applications to use it. That approach has two problems: every application that ignores the proxy setting leaks outside the tunnel, and every connection pays an extra handshake through the proxy layer before it reaches the network.

Locus creates a TUN interface instead. The client asks the operating system for a virtual network device, and the system routing table sends traffic to locus0. Because the capture happens below the application, an application does not need to know the tunnel exists — and cannot opt out of it.

The trade-off is that applications which resolve names themselves, or speak directly to a hard-coded resolver, need separate handling. There is no proxy setting to point at them, which is exactly what makes the approach leak-resistant in the first place.

2. The tunnel engine is supervised

The tunnel itself is handled by a separate engine process that the client starts and watches. The client does not assume the engine is healthy: it checks on a timer, and if the process has exited it restarts it.

  • Up to three restarts within five minutes.
  • After the third, the client stops and reports the fault rather than looping.
  • Shutdown is graceful, with a forced kill after five seconds.

A restart limit matters more than it appears. An engine that is crashing because of a configuration or platform fault will crash again immediately, and a client that restarts it forever hides the problem while leaving the tunnel unusable. Stopping and saying so is the more honest failure.

3. Per-tier traffic shaping

Each tier has its own listener on the server, and each listener is attached to a traffic control class with a bandwidth ceiling. Basic is 5 Mbps, Stream is 100 Mbps and Gaming is 200 Mbps.

The important detail is where the shaping happens. It is applied by the kernel after the tunnel has been decrypted, using an HTB queue discipline, so it does not depend on anything running on your machine. A modified client cannot negotiate a higher cap, because the cap is not part of the negotiation — it is the rate at which the server will send.

Each class also carries a fair-queue discipline so that a single saturated connection cannot starve the others on the same tier, which is what keeps latency reasonable while a large download is in progress.

4. Why UDP relay is only on Gaming

TCP guarantees ordering: if a packet is lost, everything behind it waits until it is retransmitted. Tunnelling real-time traffic over TCP therefore converts packet loss into latency spikes, which in a game looks like rubber-banding and in a voice call sounds like a stutter.

Gaming therefore carries datagrams as datagrams, with a UDP relay end to end. It is the most expensive capacity we run, because it cannot be multiplexed as neatly as TCP and it requires its own path through the network, so it is the one capability reserved for the top tier rather than given to everyone.

5. The kill switch

The kill switch is a firewall rule, not a check inside the client. Before the tunnel is established the client installs rules that block outbound traffic except to the relay, and it removes them only when the tunnel has been torn down deliberately.

The consequence, stated plainly: if the client process is killed without cleanup, traffic stays blocked until the next launch. That is the correct direction to fail, but it does mean a crash can look like a total internet outage until you reopen the app and let it tidy up.

On iOS there is no equivalent hook in the system VPN framework, so the app does not claim one. Every other supported platform has it.

6. Signed, staged updates

The client checks a manifest for a newer version and, when one exists, downloads it, verifies the size against the published bounds and the hash against the published digest, and only then swaps it into place. The previous version is retained until the new one has started successfully.

Updates are staged rather than released to everyone at once. A release carries a rollout percentage, and a given account receives it when a stable hash of its identifier falls below that threshold. The practical effect is that a bad build reaches a small, consistent fraction of clients instead of all of them, and the fraction is not chosen at random on each check.

Recovery is automatic: if the updated client fails to complete its startup handshake, the previous version is restored on the next launch rather than leaving the machine in an unusable state.

7. Activation and device binding

An account receives a subscription code. The code is validated locally for format and checksum before it is sent anywhere, so a typo fails instantly instead of consuming one of the limited activation attempts.

On first activation the server binds the code to a hardware fingerprint derived from stable machine identifiers. That binding is what enforces the per-tier device limit in practice rather than by honour.

Codes carry a checksum, so a typo is caught before it reaches the server. If you replace a machine and no longer have the original, support can unbind the code and let it activate again; every unbind is logged with a reason.

Once bound, the client checks in periodically. The interval backs off from five minutes toward two hours when everything is healthy, and includes a small random offset so that a server restart does not produce a synchronised stampede of every client at once.

If a subscription lapses, there is a 7-day grace period in which the connection keeps working. The client shows the remaining days so the lapse is not a surprise.

8. Server operations

Server configuration is applied by a set of idempotent modules, meaning each can be re-run safely without duplicating work or breaking an existing installation. Backups run hourly, are encrypted before leaving the server, and are verified by hash on arrival. A full restore to a bare machine is scripted.

Health is exposed on a single endpoint that reports whether the control plane is up. We monitor it externally and treat a failure as an incident.
