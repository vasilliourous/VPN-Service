What is in it

Features, and what they cost you

Every entry below describes a real capability, names the trade-off, and links to the technical detail. Anything that would not survive that treatment has been left out.

01 — Routing

Routing at the network layer

The client creates a TUN interface and captures traffic below your applications. No SOCKS5 proxy sits in the path, so no app can ignore a proxy setting and leak around the tunnel. Everything that leaves the machine goes through it.

Trade-off: applications that bypass system DNS and speak to a resolver directly need separate handling, because they are not using the system path we control.

How the TUN path works →

02 — Reliability

A supervised engine

The tunnel engine runs as a child process the client starts and watches. If it exits unexpectedly the client restarts it, up to three times in five minutes, and then stops and reports the fault rather than looping forever on a broken tunnel.

Trade-off: restarting resets the tunnel, so an established download will not survive an engine crash. We would rather lose a transfer than pretend a dead tunnel is up.

Engine supervision →

03 — Speed

Published speed caps

{{tiers.basic.cap}}, {{tiers.stream.cap}} or {{tiers.gaming.cap}} Mbps depending on tier, applied on the server after decryption, which is why they hold on every device and cannot be edited away in a config file.

Trade-off: Basic being slower than Stream is the product, not a defect. It is stated on the pricing page rather than buried, and we consider that arrangement honest.

04 — Latency

UDP relay on Gaming

Datagrams travel as datagrams, which is what low-latency games and voice chat need. Tunnelling UDP over TCP introduces head-of-line blocking, which shows up as rubber-banding the moment there is any packet loss.

Trade-off: UDP relay is the single most expensive thing we run, so it is the one capability reserved for the top tier rather than given to everyone.

05 — Leak safety

A kill switch that survives a crash

The kill switch is implemented as a firewall rule rather than a check inside the client, so it still holds if the client process dies. Traffic cannot escape to the open internet while the tunnel is down.

Trade-off: a hard process kill leaves traffic blocked until the next launch. That is the correct failure direction, but it does mean a crash looks like an internet outage until you reopen the app.

Kill switch detail →

06 — Updates

Signed, staged updates

Downloads are checked for size and for a matching hash before the new version is swapped in, and the previous version is kept until the new one has run successfully. Releases reach a percentage of clients first, picked by a stable account hash.

Trade-off: staged rollout means you may wait a few days behind the newest release. It is the reason a bad build reaches a fraction of users instead of all of them.

Update process →

07 — Cryptography

Standard cryptography, no exotica

Published primitives and published protocols, with no proprietary cipher and no custom handshake. Every tier is identical here — the differences between plans are speed, devices and UDP relay, and nothing else.

Trade-off: we will not invent a cipher to win a comparison table, which means we have no proprietary-sounding security claim to sell you.

08 — Privacy

No logs, on every tier

No IP addresses, no DNS queries, no destinations, no connection timestamps. Logging is not a feature you pay to enable — it is the same on Basic as it is on Gaming, and it is written into the terms so it cannot be changed quietly.

Trade-off: without logs we cannot diagnose "was my account used" the way a logging service could, and we cannot produce data we do not hold. Full detail is in the privacy policy.

09 — Devices

Device limits that mean something

Each subscription code binds to a hardware fingerprint on first activation, which is what enforces the device count rather than a policy we hope you follow. Three devices on Basic, eight on Stream, unlimited on Gaming.

Trade-off: replacing a machine is a support unbind, and each unbind is logged with a reason. Convenient, it is not — but it is why the limit holds.

10 — Billing

{{policy.graceDays}}-day grace on lapsed plans

If a payment lapses the connection keeps working for {{policy.graceDays}} days, and the client shows the days remaining in the main window. Running out of credit should not mean losing connectivity mid-task.

Trade-off: we carry the cost of those days. It is cheaper than the support burden of abrupt disconnections, so we treat it as a feature rather than a concession.

Platforms

Where the client runs

  • Windows 10 and later, with kill switch
  • macOS 12 and later, with kill switch
  • Linux, with kill switch
  • Android, with kill switch
  • iOS, using the system VPN framework
  • Routers and other devices via generated configuration

Kill switch support depends on the platform's firewall API, so iOS is the exception — the system VPN framework does not expose an equivalent hook. We would rather say that than list a feature that quietly does nothing.

Server side

How the network is run

  • Idempotent setup modules, safe to re-run
  • Hourly encrypted backups, hash-verified on arrival
  • Scripted restore to a bare machine
  • Per-tier shaping applied at the kernel queue discipline
  • External uptime monitoring on the control endpoint
  • {{network.servers}} servers we operate on our own autonomous systems

Setup being repeatable matters more than it sounds: it is what makes rebuilding a server during an incident a routine task rather than a risky one.
